## Module 1 — RAG один шар глибше

- **LLM** = функція «текст → наступний токен» у циклі. Знає лише те, що в prompt + заморожене у вагах; без контексту — галюцинує впевненим тоном. Єдиний runtime-вхід — prompt, обмежений **context window**.
- **RAG** = дисципліна «покласти правильні факти в context window на момент запиту». Крок «augment» — буквально конкатенація рядків, ніякого «модель звертається до бази».
- **RAG vs fine-tuning:** документи змінюються → fine-tune треба повторювати, RAG просто оновлює сховище; fine-tuned модель не цитує надійно; не можна «розшарити» окремий документ (access control); RAG тримає знання там, де його можна інспектувати й атрибутувати. Fine-tuning змінює *як* модель говорить, RAG — *які факти* вона має.
- Класичний RAG-цикл: індексація (load → chunk → embed → store) і запит (embed питання → top-k → augment → generate → (attribute)).
- **Embedding** — фіксований вектор (384/768/1024/1536…) від окремої малої моделі; близькі за змістом тексти — близькі вектори. Порівняння — **cosine similarity** (−1…1). Одна й та сама модель для індексу й запиту.
- **Chunking** — компроміс: завеликі chunks → розмитий сигнал і марнування context window; замалі → втрата контексту («It raised $2M» — що «it»?). Старт ≈ 200–500 токенів з 10–20% overlap. *У проєкті chunking немає — документи малі, а одиниця пошуку — вузол графа з його описом.*
- **Brute-force vs ANN (HNSW):** порівняти запит з кожним вектором дорого; HNSW дає швидкість коштом того, що не гарантує абсолютно точний top-k (recall < 100%).
- **Hybrid (semantic + BM25/lexical):** семантика ловить синоніми; лексика — точні терміни, імена, коди. Реальні системи комбінують (сума з вагами або Reciprocal Rank Fusion). *У проєкті лексика з'явилась лише в entity resolution (fulltext), а не в retrieval на query — це відкритий пункт.*
- **Reranking:** після дешевого пошуку кандидатів — сильніший (дорожчий) другий прохід, напр. LLM «це релевантно питанню X? так/ні» над 8–20 кандидатами.

### Асиметричні task-префікси (`nomic-embed-text`)

Модель тренувалась на парах `search_query: …` ↔ `search_document: …`. Без префікса вхід «поза розподілом» і потрапляє в «нетюновану» область простору (anisotropy — простір стискається у вузький конус), тому **дискримінація** (здатність відокремити релевантне від нерелевантного) падає. Тому `embedDocument` і `embedQuery` — два окремі публічні методи, а загальний `embed` — приватний: щоб ніхто не переплутав бік і не отримав тихо гірший retrieval. Префікси — специфіка конкретної моделі; при зміні моделі це треба переглянути.

## Module 2 — Від vector RAG до Graph RAG

- Flat RAG відбирає за **схожістю до питання**, Graph RAG — за **структурою**. Приклад, де flat RAG провалюється: «перелічи всі проєкти, які спонсорує Acme» при 40 документах із різними проєктами — у питанні мало семантики, кожен chunk каже «Project X…», top-k обрізає частину (та сама проблема з `k` теоретично є й у графі, якщо його обмежити). Для enumeration / aggregation / global-питань граф кращий.
- Multi-hop: «хто відповідає за білінг?» → `billing ← RESPONSIBLE_FOR ← platform team ← MANAGES ← maria` — два hops; у flat RAG факт про Марію просто губиться в окремому chunk.
- Але **граф не кращий за вектор завжди**: його ціна — витягти entities/relations з кожного фрагмента (дорого, схильно до сміття).
- **Cypher**: напрямок задається стрілкою (`-[:MANAGES]->` / `<-[:MANAGES]-`); properties — через крапку (`d.name`), двокрапка лише для labels/relationship types. Приклад зворотного запиту: `MATCH (p:Person {name:'Марія'})-[:MANAGES]->(t:Team)-[:RESPONSIBLE_FOR]->(d:Domain) RETURN d.name`.

## Module 3 — Граф з тексту

- LLM **не пише сирий Cypher**; вона повертає **structured output** (JSON за схемою), а код валідує і пише фіксованим параметризованим Cypher.
- Джерела «сміття» в графі: різні написання однієї сутності (Acme / Acme Corp / ACME Inc.), синоніми relations (`MANAGES` vs `LEADS`), сутності-речення, надто загальні relations.
- Лікування на етапі extraction: чіткі правила в промпті, few-shot, передача відомих сутностей/типів у промпт (**зроблено**: relation vocabulary). Лікування після extraction: нормалізація (зроблено) і **entity resolution** (зроблено).
- Ідея автора проєкту (7 вер): дедуплікувати через embedding назв → саме це стало кандидатним кроком entity resolution, а перевірку «чи справді та сама» (LLM yes/no) додано поверх.
- Інкрементальне оновлення: upsert за ім'ям, перерахунок embedding зачеплених вузлів.

## Module 4 — Алгоритми graph retrieval

Три «діри» наївного підходу й відповіді:

1. **Як з питання отримати seed nodes?** LLM витягує фрази → **embedding + vector index** (Stage 1). Точний збіг крихкий (множина, синоніми, транслітерація).
2. **Як розширюватись від seeds?** Наївно `MATCH (s)-[*1..2]-(x)` забирає сміття. Відсікати за релевантністю по дорозі не можна — **premature pruning**: проміжна нода («platform team») семантично не схожа на питання, але саме вона веде до відповіді. Відповідь — **Personalized PageRank**.
3. **А якщо seeds немає?** («які основні теми в усіх документах?») → PPR вироджується. Відповідь Microsoft GraphRAG — **communities** (Leiden) + LLM-summaries + map-reduce global search. *Stage 5, не зроблено.*

### PPR / HippoRAG

- Випадкове блукання, що з імовірністю (1 − damping) **телепортується назад у seed nodes**. Score ноди = наскільки вона досяжна від seeds; **плавно спадає з відстанню** (прямий сусід — високий, через один вузол — нижчий). У GDS це `gds.pageRank` з `sourceNodes`.
- Перевага для цього проєкту: **один прогін алгоритму замість LLM-виклику на кожному кроці обходу** — дешево й швидко на локальній моделі.
- Дві різні частини: **семантика** (пошук seeds через vector index Neo4j) і **структура** (PPR у плагіні GDS, про семантику нічого не знає).
- Microsoft GraphRAG vs HippoRAG: перший — дорогий indexing (communities + summaries), добрий для global; другий — легший indexing, добрий для multi-hop фактичних питань. Вибір проєкту — HippoRAG-стиль для local search, MS-стиль планується для global (Stage 5).

## Module 5 — Агентний шар

- **Агентна поведінка** = LLM сама вирішує, що робити далі, у циклі. Три поведінки з прикладів: **routing** (дешева стратегія для простого факту), **query decomposition** («порівняй Platform і Growth» → два окремі retrieval), routing у **global search**.
- **Fixed pipeline vs ReAct-цикл:** у фіксованому — порядок кроків прописаний наперед; у ReAct LLM щоітерації обирає дію (tool call / фінальна відповідь), результат повертається в історію, керування **повертається в LLM**, цикл, доки вона не скаже «досить».
- **Tool/function calling** — формалізація «як відповісти»: разом із prompt передаються схеми tools; модель повертає структурований виклик.
- Корекція, зроблена в діалозі: перша схема автора проєкту була **plan-execute** (LLM віддала обидва виклики масивом, і код виконав обидва) — а не чистий ReAct; пропущено поворот циклу назад у LLM після отримання результатів. Також: порожній бік порівняння → відповісти «даних нема», а не домислювати.
- Практична деталь: `/api/generate` Ollama одноразовий, без історії; агентному циклу потрібен `/api/chat` з масивом повідомлень і нативним параметром `tools`.

## Module 6 — Локальні LLM

- Для агентного циклу модель мусить: надійно видавати structured output / tool calls, мати достатнє **реальне** (не рекламне) context window, коректно слідувати інструкціям.
- **Extraction — слабке місце малих моделей** і окрема важча задача: 1 LLM-виклик на chunk → сотні викликів на великий документ. Тому проєкт тільки для малих документів. Запасний план: винести лише ingest на hosted-модель (він offline).
- Залізо: MacBook Air M1, 16 GB unified memory, без кулера → 7–8B (Q4, ~5 GB) комфортно; 14B тісно; 32B+ непридатно; тротлінг при тривалому навантаженні.
- Runner: Ollama (обгортка над llama.cpp, `format: json`, бібліотека моделей). vLLM — для throughput, не для цього проєкту.

## Module 7 — Explainability, provenance, evaluation (формально не проходили)

- **Explainability:** повернути **що саме** з графа лягло в основу відповіді. У проєкті це `subgraph` (nodes + edges) — і для тексту відповіді, і для майбутньої правої панелі UI. З Module 5 лишилась ще одна ідея: у агентного циклу trace «думка → tool call → результат» сам є артефактом пояснення (поки не повертається назовні).
- **Provenance:** кожен факт має пам'ятати документ/chunk-джерело. Не реалізовано, відкладено до Stage 6 (див. [03](03-roadmap-stages.md)).
- **Evaluation:** калібрувальний набір пар «питання → очікувані вузли», **включно з негативними** (`expectedNodes: []`), прогін pipeline при різних threshold/topN, підрахунок recall/precision, вибір балансу. Той самий принцип, що train/validation. Без цього три числа (0.6 / 0.5 / 15) лишаються здогадками. RAGAS-метрики: faithfulness, answer relevance, context precision/recall.

## Корисні «чому» для співбесіди

- *Чому GraphRAG, а не flat RAG?* — multi-hop і enumeration; структура, а не схожість.
- *Чому PPR, а не BFS 1–2 hops?* — premature pruning; один прогін замість LLM на кожному кроці; плавна деградація з відстанню.
- *Чому не `createReactAgent`, а `StateGraph`?* — контроль над логікою і власний state-акумулятор; бібліотека лишається, прибирається лише плумбінг. У продакшні — LangGraph/Vercel AI SDK цілком нормальний вибір; руками цикл писали заради розуміння.
- *Як боретесь з галюцинаціями?* — grounding у system prompt, абстенція («не знаю»), опис вузла будується кодом із реальних ребер; fail-closed у entity resolution.
- *Що б зробили далі?* — eval-harness, калібрування порогів, hybrid retrieval, communities для global-питань, provenance.
